How to choose an MCP connector

A practical filter for picking connectors that will still work in six months, based on what the registry actually tells you.

8 minute read. Updated 2026-07-30.

The official registry holds more than nineteen thousand server records. Most people approach that number by searching for the product they already use, installing the first result and moving on. That works until it does not, and the failure is usually not dramatic: a connector goes quiet, a token stops being accepted, an assistant starts returning empty results and nobody notices for a week.

This guide is the filter we apply before a connector earns a profile page on this site. It takes about two minutes per candidate and it removes most of the connectors that will waste your time.

Start from the client, not the connector

The first question is not which connector is best. It is which connectors your client can physically talk to.

Clients divide into three groups. Some run a local process and speak to it over stdio. Some attach a hosted server over HTTPS. Most do both, but not all of them, and the two that do only one thing are common enough to matter. ChatGPT will not launch a process on your machine. Zed will not attach a hosted endpoint without a local bridge in front of it.

If you pick a connector before you check this, you can spend an hour debugging a file that was never going to load. Our client reference lists the transports each client documents, along with where its config file lives.

Read the namespace before the description

Every record in the registry sits under a reverse domain namespace, and that namespace is verified before publication. There are two shapes and they mean different things.

A name beginning io.github. means the publisher proved control of that GitHub account. A name built from a company domain, such as com.example, means the publisher proved control of that domain. The second is a stronger signal, and it gets stronger still when the domain matches the website on the same record.

None of this is a security review. The registry says so plainly in its moderation policy: listing is intentionally light touch. What namespace verification gives you is an answer to a narrower question, which is whether the publisher is who the record says they are. That is worth knowing, and it is not the same as knowing the code is safe.

Check that the record can be checked

A connector record that publishes neither a repository nor a website is a dead end. There is nothing to read, nothing to file an issue against, and no way to tell whether the project is maintained. We refuse to build a profile page for those records, and you should apply the same rule.

When a repository exists, spend thirty seconds on it. You are looking for three things:

  • A commit in the last few months. Protocol revisions land regularly, and an unmaintained server will drift out of compatibility.
  • A readme that describes the tools the server exposes. If the author cannot list them, the model will discover them at runtime and you will have no idea what you granted.
  • An issue tracker with replies in it. An unanswered tracker is a reasonable proxy for an unanswered support request later.

Prefer a pinned version

Registry packages can declare a version. When they do, the config we generate pins it, and you get a reproducible install. When they do not, your package manager resolves whatever is latest at the moment the client starts, which means the tool surface of your assistant can change without you doing anything.

For a personal setup that is a nuisance. For a shared project file committed to a repository, it is a real problem, because two people on the same team can end up running different code from the same config.

Understand the credential before you paste it

The credential shape tells you a lot about how much care a connector needs.

No credential. Nothing to leak, nothing to rotate. These are the best connectors to test a client with, and the ones we group in the no credential collection.

An API key. A long lived secret that ends up in a config file. Scope it as narrowly as the upstream service allows, and remember that a local process inherits your shell environment, so it may already be able to see variables you did not intend to share.

An authorisation flow. A consent screen in a browser, a scoped grant and a session you can revoke. Almost always the better option when a service offers both. Read the scopes on the consent screen rather than the description on the marketing page, because the scopes are the actual permission.

Count the tools

Every tool a connector exposes is a line in the prompt your model reads before it does anything. Clients handle this differently, and several apply a ceiling on how many tools they will offer at once. A single bridge connector that exposes ninety tools can crowd out four focused connectors that would have been more useful.

The practical rule: prefer several small connectors over one that claims to do everything, unless the one that claims to do everything is the only way to reach a system you need.

What we do not use as a signal

We do not rank connectors by stars, downloads or any popularity number. Those numbers are not available consistently across the registry, they are easy to inflate, and they measure attention rather than fitness. Our completeness score measures how much a publisher actually published, which is a smaller claim and a more honest one. The full breakdown is on the methodology page.

A two minute checklist

  1. Does my client support the transport this connector publishes?
  2. Is the namespace a verified domain, or at least a GitHub account that matches the linked repository?
  3. Is there a repository or a website I can open right now?
  4. Has anything changed in the last six months?
  5. Is the package version pinned?
  6. What credential does it want, and can I scope that credential to read only?
  7. How many tools does it add, and do I need all of them?

If a connector clears all seven, install it. If it fails on the first or the third, move on. Everything in between is a judgement call, and the judgement gets easier once you have made it a few times.
