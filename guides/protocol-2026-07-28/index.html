What the 2026-07-28 protocol revision changes

The current specification revision, what moved since the previous one, and how to tell whether your client and servers are aligned.

6 minute read. Updated 2026-07-30.

The current revision of the Model Context Protocol specification is dated 2026-07-28. If you are reading a tutorial that references an older revision, the shape of what it describes is probably still right and the details may not be.

This guide is deliberately short, because the specification changelog is the authoritative document and it is public. What follows is how to use it.

Read the changelog, not the summary

The changelog lists what changed between revisions in the project own words. It is the only source that stays correct, and it takes less time to read than most secondary explanations of it.

Two areas have moved most often across revisions and are worth checking first whenever you upgrade something:

Authorisation. The model for HTTP based servers has been refined repeatedly. The authorization section of the current revision is where to look when a hosted connector suddenly stops accepting a session that worked last month.

Transports. The transports document defines stdio and streamable HTTP. Server sent events is the older HTTP transport. It still appears on registry records and clients still accept it, but a connector published only as an SSE endpoint is one that will need attention eventually.

Revision mismatch is the usual culprit

Client and server negotiate a protocol revision when they connect. When something that used to work stops working after an update, the cause is very often that one side moved and the other did not.

The symptom is rarely a clear error. More commonly a server connects, reports fewer tools than it should, or fails on one specific capability while the rest keeps working.

The fix is boring and reliable: update the client, update the server package, and try again before investigating anything else.

What this means for connector operators

Pin versions in shared config. A project file that resolves whatever is latest at startup will pick up a protocol change without anyone deciding to. Our generated config pins the version whenever the registry record publishes one.

Keep clients current. Protocol work lands in clients at different speeds. The client capability matrix published by the project is the reference for what a given client implements.

Prefer streamable HTTP for new hosted work. It is the current HTTP transport. Publishing only SSE in 2026 is choosing a migration for later.

Expect authorisation to keep moving. It is the most actively developed part of the protocol because it is the part with the most real world constraints. Build the revocation path into your setup rather than assuming a token lasts forever.

What this means for the catalog

ConnectorZone reads the registry rather than the specification, so a revision change does not alter our data directly. It does change what a compatibility verdict is worth, which is why every verdict on this site records the date the client documentation behind it was read.

When a revision lands that changes which transports a client accepts, we reread the client documentation and update the client pages. Those updates are listed on the changelog, and the methodology behind the verdicts is on the methodology page.

A three line upgrade check

  1. Does the client release note mention a protocol revision? If yes, update servers too.
  2. Does a previously working hosted connector now fail to authorise? Read the authorisation section of the current revision.
  3. Does a server connect but report fewer tools than before? Suspect revision mismatch before suspecting the connector.
