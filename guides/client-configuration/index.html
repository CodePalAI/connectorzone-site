Configuring MCP in every major client

Where each client keeps its config, which key name it expects and the specific mistakes that stop a server loading.

9 minute read. Updated 2026-07-30.

The protocol is standard. The configuration is not. Nine widely used clients read MCP server definitions from nine different places, using at least four different shapes, and the errors they produce when you get it wrong are mostly silence.

This is the reference we wish existed when we started. Every connector profile on this site generates the correct block automatically, but it helps to know why the blocks differ.

Four shapes, not one

The mcpServers object. Claude Desktop, Claude Code, Cursor, Gemini CLI and Windsurf all use a top level mcpServers object mapping a name to a definition. This is the closest thing to a common format, and it is still not portable, because the remote field name differs.

The servers object. VS Code uses servers, not mcpServers, and each entry carries an explicit type field. A block copied from Cursor will parse as JSON and then do nothing, because the key VS Code looks for is absent.

The context_servers object. Zed nests servers inside the editor settings file under context_servers, and each entry needs a source field. Nothing else uses this shape.

TOML. Codex CLI configures MCP in ~/.codex/config.toml using [mcp_servers.name] tables. Every JSON snippet on the internet is wrong for it.

Where the files live

Client Path
Claude Desktop ~/Library/Application Support/Claude/claude_desktop_config.json on macOS, %APPDATA%\Claude\claude_desktop_config.json on Windows
Claude Code .mcp.json in the repository, or ~/.claude.json for user scope
Cursor .cursor/mcp.json in the project, or ~/.cursor/mcp.json globally
VS Code .vscode/mcp.json in the workspace, or the user config via the command palette
Gemini CLI ~/.gemini/settings.json, or .gemini/settings.json in a project
Windsurf ~/.codeium/windsurf/mcp_config.json
Codex CLI ~/.codex/config.toml
Zed ~/.config/zed/settings.json, or .zed/settings.json in a project
ChatGPT No file. Connectors are added in settings, and the API takes a URL in the request body

Full details, including which transports each client documents and what it cannot do, are on the client pages.

The remote field trap

This is the most common failure we see, and it produces no error message.

Attaching the same hosted endpoint requires a different field name depending on the client:

  • Cursor, Claude Code and Claude Desktop use url.
  • Gemini CLI uses httpUrl for streamable HTTP and url for server sent events. Using url for a streamable HTTP server selects the wrong transport rather than failing.
  • Windsurf uses serverUrl.
  • VS Code uses url together with "type": "http".

A block that works perfectly in one editor will load as an empty server in another. If a server appears in the client list with zero tools, check the field name first.

Secrets in config files

Config files get committed. That is not a hypothetical.

VS Code has the best answer: an inputs array declares a prompt, marks it as a password, and the value never lands in the file. Claude Code and several others expand shell variables, so ${SERVICE_TOKEN} in the file resolves from your environment at startup.

If your client supports neither, keep the file out of version control and treat it with the same care as a credentials file, because that is what it is.

Restart behaviour

Clients differ on whether they notice a changed file.

Claude Desktop needs a full quit and relaunch. Closing the window is not enough on macOS, where the application keeps running. This is responsible for a large share of the reports that a config change did nothing.

Editors generally reload on demand and expose a command to restart a single server, which is much faster to iterate against.

Command line clients pick up changes on the next run.

Confirming it worked

Every client has a way to list what it discovered, and checking it takes five seconds:

  • Claude Code and Gemini CLI: the /mcp command.
  • Cursor and VS Code: the MCP panel in settings, which lists servers and their tool counts.
  • Claude Desktop: the tools indicator in the composer.
  • Codex CLI: the /mcp command.
  • Zed: the agent panel server list.

A server that shows up with zero tools has connected and returned nothing, which usually means a missing credential. A server that does not show up at all has not been read, which usually means the wrong key name or invalid JSON.

Tool budgets

Several clients cap how many tools they will present to the model at once. When you cross the cap, tools disappear without a warning, and which ones survive is not always predictable.

If you have a large bridge connector attached alongside several focused ones, disable the bridge while you work on something specific. Fewer, sharper tools produce better results anyway.

The fastest way to debug

  1. Validate the file. A trailing comma in JSON breaks the whole file, not just one entry.
  2. Confirm the top level key matches the client. servers for VS Code, context_servers for Zed, mcpServers for the rest, TOML tables for Codex.
  3. Run the command by hand in a terminal. If npx -y some-package fails there, it will fail in the client too, and the terminal will tell you why.
  4. Check the remote field name against the table above.
  5. Restart the client properly, which for Claude Desktop means quitting it.
  6. Open the client server list and read the tool count.

If you get through all six and it still does not work, the connector profile page on this site lists the publisher repository, which is the right place to file the issue.
