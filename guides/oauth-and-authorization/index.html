OAuth and authorisation in MCP

How authorisation works for HTTP based MCP servers, what the consent screen is really telling you, and where keys still make sense.

8 minute read. Updated 2026-07-30.

Two things get called authentication in MCP conversations and they behave very differently. One is a key you paste into a config file. The other is a browser flow that produces a scoped, revocable grant. Knowing which one you are dealing with changes how carefully you need to treat the setup.

The key you paste

Most local connectors want an environment variable. The registry record declares it, our profile pages render it into the right place in the config block, and you replace the placeholder with a real value.

This is simple and it has three durable problems.

The value sits in plain text on disk, in a file your client reads at startup. Anything that can read your home directory can read it.

It rarely gets rotated, because rotation means editing a file and restarting a client, and nobody schedules that.

It is usually scoped by the upstream service rather than by the grant. If the service only issues account wide keys, the connector gets account wide access no matter how little it needs.

Some clients help. VS Code supports an inputs array that prompts for a secret once and stores it outside the file you commit. Several clients expand shell variables, so you can reference ${SERVICE_TOKEN} and keep the value in your environment. Use those mechanisms where they exist. Our per client pages note which ones do.

The flow you approve

HTTP based servers can implement an authorisation flow instead. The specification describes the model in detail, and the practical shape is familiar to anyone who has connected two web services together.

Your client discovers where the server expects authorisation to happen. A browser opens. You sign in to the upstream service, read a consent screen listing what the client is asking for, and approve or refuse. The client receives a token it can use, usually alongside a refresh token, and the server accepts requests carrying it.

Three things make this better than a pasted key.

The grant is scoped. The consent screen lists specific permissions rather than handing over an account.

The grant is revocable. You can end it from the upstream service without touching your config.

The secret is shorter lived. Access tokens expire. A leaked one has a shelf life.

Read the consent screen, not the marketing page

This is the single most useful habit in this guide.

A product page will say a connector reads your calendar. The consent screen will say it requests read and write access to all calendars on the account. Those are different, and only one of them is the permission you are actually granting.

If the scopes are wider than the described feature set, that is worth a pause. Sometimes the reason is boring: the upstream API only offers coarse scopes. Sometimes the reason is that the connector does more than the description admits. You cannot tell which from the outside, but you can decide whether the wider grant is acceptable.

Where tokens end up

Every client stores this differently, and the storage location becomes as sensitive as a password.

Desktop applications generally keep tokens in an application data directory. Command line tools generally keep them in a dotfile under your home directory. Neither is encrypted by default in most setups.

Two practical consequences. First, backing up your home directory backs up your grants. Second, handing someone your laptop hands them your sessions. If you share a machine, revoke before you hand it over.

What changed in the 2026-07-28 revision

The current specification revision is 2026-07-28. Authorisation has been one of the most actively developed parts of the protocol, and the changelog is the correct place to check what moved rather than relying on a blog post from six months ago, including this one.

The practical advice that survives every revision: keep your client current. Authorisation changes are exactly the kind of thing that produces a confusing failure when a client and a server are built against different revisions of the spec.

When a key is still the right answer

Authorisation flows need a browser and an interactive user. Neither exists in a scheduled job, a container in a build pipeline or an agent running unattended on a server.

For those cases a scoped key is correct. Make it as narrow as the service allows, store it in whatever secret manager the environment already has, and rotate it on a schedule that somebody owns. The failure mode of a key is that it lives forever, so give it a defined lifetime deliberately.

A short checklist

  1. Does this connector offer an authorisation flow? If yes, use it.
  2. If it wants a key, is there a scoped key type available? Create the narrowest one.
  3. Where does the secret land on disk? Can my client keep it out of a committed file?
  4. What exactly did the consent screen ask for?
  5. How do I revoke this, and have I checked that path works?
  6. If this is unattended, who owns rotation and when does it next happen?

Connectors that use an authorisation flow are grouped in the OAuth first collection, and every connector profile page states the credential shape the registry record declares.
