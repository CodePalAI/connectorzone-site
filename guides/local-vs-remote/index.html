Local servers or hosted endpoints

The trade between running a connector on your machine and attaching one over HTTPS, and how to tell which your situation calls for.

7 minute read. Updated 2026-07-30.

Every connector in the catalog is delivered one of two ways. Either you run it as a process on your own machine and talk to it over standard input and output, or somebody else runs it and you attach it over HTTPS. The protocol treats both as first class. Your client might not.

The short version

Run it locally when the connector needs access to something only your machine has: files on disk, a database inside your network, a tool already installed, a credential you do not want to leave the laptop.

Attach a hosted endpoint when the connector wraps a service that already lives on the internet, when you want the same setup on several devices, or when your client cannot launch a process at all.

What local actually means

A local server is a command your client starts. For a package on npm that is usually npx, for a Python package uvx, for a container image docker run. The client writes JSON to the process standard input and reads responses from standard output.

The consequences are worth stating plainly.

The process runs as you. It sees your files, your environment variables and your network. If you have exported a cloud credential in your shell profile, a local MCP server can read it, whether or not it has any business doing so.

The first start is slow. npx and uvx download the package before anything happens, which is why a client sometimes appears to hang for twenty seconds on first launch and then behaves normally.

There is no network hop for the tool call itself, so latency is whatever the underlying work costs. For a connector that reads local files, that is very fast.

The setup does not travel. A config file on your laptop does nothing for your phone, and a teammate needs the same runtime installed before the same file works for them.

What hosted actually means

A hosted server is a URL. Your client opens an HTTP connection, usually streamable HTTP, occasionally the older server sent events transport, and the operator of that URL runs the code.

Nothing installs, which removes an entire class of problem. There is no runtime to manage, no first start download, and the same endpoint works from every device signed into the same account.

Every argument goes to the operator. If your assistant sends a customer name to a hosted connector, that name is now in someone else logs. This is the central trade and it is not mitigated by the connector being well written.

Authentication is usually better. Hosted servers commonly implement an authorisation flow, which gives you a consent screen and a revocation path instead of a key in a text file.

Availability is theirs. If the endpoint is down, your tool is down, and you have no ability to fix it.

Which clients accept which

Most clients accept both, but the exceptions are the ones that catch people out.

ChatGPT and the OpenAI Responses API accept hosted endpoints only. There is no mechanism for either to launch a process on your machine, so a connector published only as an npm package cannot be used there without you deploying it somewhere first.

Zed runs local context servers. A hosted endpoint needs a local bridge process in front of it.

Everything else in our client reference documents both, though the key names and field names differ enough that a config block is rarely portable. Gemini CLI uses httpUrl for streamable HTTP and url for server sent events. Windsurf uses serverUrl. Cursor and Claude use url. Copying a working block from one client to another is the most common reason a server silently fails to load.

Transport details that matter

The specification defines stdio and streamable HTTP as the current transports. Server sent events is the older HTTP transport and it still appears on a small number of registry records. It works where clients support it, but a connector that only publishes an SSE endpoint is a connector that will need attention at some point.

When a record publishes both a package and a hosted endpoint, you get a genuine choice. Our profile pages show every published option and generate the correct block for each client against the option that fits it best.

Self hosting a local connector

There is a third path that people forget: take a connector published as a container image and run it yourself behind your own HTTPS endpoint. You keep the data inside your perimeter and you gain the multi device reach of a hosted server. The cost is that you now operate a service.

This is the right answer more often than it gets chosen, particularly for teams who want one reviewed connector shared across an organisation rather than fifteen laptops each running their own copy with their own key.

A decision you can make in ten seconds

  • Does the connector need something only this machine has? Run it locally.
  • Does my client refuse to run local processes? Use the hosted endpoint, or self host.
  • Do I need this on more than one device? Prefer hosted.
  • Is the data sensitive enough that I would not paste it into a third party web form? Do not send it to a third party endpoint either.
  • Am I setting this up for a team? Self host, or pick a vendor published hosted endpoint and read the terms.
