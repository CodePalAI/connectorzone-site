Methodology

Every number, verdict and page on this site comes from a rule you can read here. Where a rule is imperfect, this page says so.

Updated 2026-08-02

Where the data comes from

The only source of connector records is the official Model Context Protocol Registry. We read https://registry.modelcontextprotocol.io/v0.1/servers with version=latest, following cursor pagination until the registry stops returning a cursor. The current snapshot holds 19,630 records and was taken on 2 August 2026.

Registry data is published under CC0 1.0. Publisher descriptions are reproduced verbatim with attribution on each profile page. Everything else on a profile page, including the one line summary at the top, is written by ConnectorZone from structured fields rather than paraphrased from the publisher text.

The snapshot is committed to the repository so any build produces the same site. Freshness calculations are measured against the snapshot timestamp, not against the clock, which is what makes two builds of the same data byte identical.

What a registry listing does not mean

A listing in the official registry is a namespace ownership check, not a security review. ConnectorZone does not execute connectors and does not audit their code. Treat every connector as third party software with the access you grant it.

Namespace ownership is verified before publication, two ways. A name beginning io.github. means the publisher proved control of that account. A name built from a domain means the publisher proved control of that domain. We label the second as vendor published when the domain also matches the website on the record, because that pairing is the strongest ownership signal available. None of these labels is a security judgement.

The completeness score

The score answers one question: how much of what an operator needs before wiring this connector into an assistant is actually published? It is out of 100 points, then expressed as a percentage. It is not a rating, not a review and not a popularity measure.

DimensionWeightWhat earns points
Namespace provenance28A verified domain namespace matching the website scores highest, a verified account namespace next, everything else lowest.
Published references24A repository, a website, a title, icons and a description long enough to be informative.
Install clarity22A runnable command or endpoint, a pinned version, described environment values, and more than one delivery route.
Release freshness14How recently the registry record was updated, on a ramp from thirty days to over a year.
Credential hygiene6Hosted endpoints over TLS, secrets declared as secrets, and no credential sitting in a command line argument.
Client reach6How many of the 9 tracked clients the record can reach. Deliberately a small weight, because the protocol is standard and almost every record reaches almost every client.

Which records get a page

5,390 of 19,630 records are held out of the catalog. A record needs all of the following to earn a profile page:

  • An active status in the registry.
  • At least one runnable package or hosted endpoint.
  • A description of at least 45 characters.
  • A repository or a website, so something on the page can be checked by a reader.
  • A completeness score of at least 38.
  • A position within the first 24 records from its publisher, ranked by score. Bulk publishing is common in the registry, and without this ceiling a single generated catalog would become most of the directory.

Which pages search engines see

12,887 profiles are indexable. The rest carry a noindex, follow directive and stay out of the sitemap, while remaining fully browsable. A profile is kept out of the index when its score is below 50, when its description is duplicated across several registry records, or when the description exceeds the length ceiling. Every profile page states its own reason in the sidebar.

Per client install pages are the most expensive surface on the site, so they are capped explicitly. Only 420 connectors receive them, chosen as the highest scoring records that also score at least 72, publish both a repository and a website, reach at least three clients, and are within the first 3 such records from their publisher.

How compatibility verdicts are produced

A verdict is the result of matching what a registry record publishes against what a client documents. If a record publishes a local package and the client documents stdio support, the verdict is supported. If a record publishes only local packages and the client cannot launch processes, the verdict is unsupported and the page says a self hosted deployment would be needed.

Confidence is labelled honestly. Almost every verdict is derived, meaning it follows from the rule above. Unverified means the record is missing something needed to judge. We never mark a verdict as tested, because ConnectorZone does not execute connectors. Each verdict carries the date the client documentation behind it was read.

How categories are assigned

Only a small minority of registry records carry publisher supplied categories, and those use inconsistent vocabularies, so ConnectorZone derives a category from the server short name, title, description, repository path and any publisher keywords. Rules are ordered by priority and the highest priority match wins.

This is keyword matching and it is imperfect. 5,296 connectors sit in general utilities, which is the group for records that matched no specific rule. That number is a measure of how specific registry descriptions are, and we would rather show it than pretend to a precision the data does not support.

What we refuse to publish

  • Ratings, stars or review scores, because we have no review process behind them.
  • Download or popularity counts, because they are not consistently available and are easy to inflate.
  • Security assessments, because we do not audit code.
  • Claims that an install was tested, because none were.
  • Generated comparison pages for arbitrary connector pairs.
  • Publisher descriptions presented as ConnectorZone editorial.

Corrections

If a page here is wrong, tell us on the report page and we will fix or remove it. Registry data itself is corrected by the publisher through the registry, and our next sync picks the change up. The data status page shows exactly which snapshot the current site was built from.
